# Messenger Matrix Local Synapse Harness

Status: MSG-MX-004 exact local-development infrastructure; not a Messenger
connector, account session, product backend, hosted service, or production
deployment.

## Exact lanes

Python Core owns six separately declared lanes. Catalog visibility does not
make them globally callable.

| Lane | Domain/capability | Side effect | Approval posture |
|---|---|---|---|
| `matrix.harness.inspect` | `messages/read` | local ownership/status inspection | policy plus exact mission lease |
| `matrix.harness.smoke` | `messages/read` | bounded loopback liveness read | policy plus exact mission lease |
| `matrix.harness.start` | `messages/execute` | start disposable local resources | fresh exact LocalApprovalAuthority result plus exact mission lease |
| `matrix.harness.fixture_seed` | `messages/mutate` | create transient synthetic fixtures | fresh exact LocalApprovalAuthority result plus exact mission lease |
| `matrix.harness.stop` | `messages/execute` | stop owned local resources | fresh exact LocalApprovalAuthority result plus exact mission lease |
| `matrix.harness.reset` | `messages/mutate` | remove exact owned resources and state | fresh exact LocalApprovalAuthority result plus exact mission lease |

Every request binds the exact capability, adapter, provider, target, project,
image, config, port, lifecycle generation/state, mission/run, lease, deadline,
budget, idempotency ref, and complete request fingerprint. Policy, current
approval where required, AuthorityLease, budget, readiness, kill switch,
safe-disable, ownership, and replay posture are re-evaluated at the atomic
pre-start boundary. An approval ref identifies a record only.
The API and CLI may ask Python Core to issue the one command-bound mission
lease through the canonical AuthorityLease store. Mutating leases and actions
still require explicit confirmation and separate exact LocalApprovalAuthority
validation; neither surface writes a lease directly or grants standing
`messages` authority.

## Packaging and containment

The harness uses only the pre-provisioned official Synapse image
`matrixdotorg/synapse` at the exact digest recorded in
`packaging/messenger-matrix-harness/provider_lock.json`. Runtime Compose uses
`pull_policy: never` and `--pull never`; it cannot download an image. The
service publishes only the safe loopback port ref for `127.0.0.1:18008`, uses
closed registration, no federation or public rooms, SQLite disposable state,
a dedicated no-masquerade bridge with loopback-only host binding, a read-only
root filesystem, an explicit non-root host UID/GID, dropped capabilities,
bounded CPU/memory/PIDs/output, disabled Docker logging, and a 30-minute
process lifetime. Synapse exposes only its client resource; federation
listeners, statistics reporting, trusted key servers, and federation targets
remain disabled.

The backend accepts only the fixed repository `.uaa` harness state scope,
rejects symlink/FIFO/device substitution, fingerprints all package inputs and
the resolved Docker binary, serializes lifecycle changes with a physical
no-follow lock, and binds a monotonic generation plus ownership ref. Docker
resources require the exact project and owner labels, image digest, and service
name. Failed start/reset cleanup must prove zero residual owned resources;
unknown cleanup truth becomes `recovery_required` and retained state is not
silently deleted. Safe-disable is set with
`UAA_MATRIX_HARNESS_SAFE_DISABLE=1` (also accepting `true`, `yes`, `on`,
`enabled`, or `engaged`, case-insensitively). It blocks start, seed, and smoke
while leaving read-only inspect plus exact stop/reset containment eligible.
Changing it requires a fresh process environment. The global AuthorityLease
kill switch is stricter: the dispatcher blocks every new harness command,
including stop/reset. Exact governed cleanup therefore requires disengaging
the global kill switch first; if that cannot be done, owned-resource cleanup is
recovery work and is never reported as a successful governed receipt.

## Synthetic fixtures and evidence

The helper creates two plan-version-stable synthetic users, a Space, a private
room, an `m.direct` room, messages, a reply, and a reaction only inside the
disposable server. Credentials remain random and transient. Synthetic content
is generated by the bounded helper and never returned. A content-free marker
prevents a second seed from appending another fixture set in the same
lifecycle. These fixtures are intentionally unencrypted; encryption,
verification, backup, and recovery belong to MSG-MX-007.

API, CLI, dispatcher, and backend results contain only safe refs, bounded
counts, reason/blocker codes, redaction posture, and content-free receipts.
They omit Docker output, provider payloads, credentials, message bodies, local
paths, environment values, usernames, and hostnames. Successful operations
return safe lifecycle generation/state refs for the next exact command. CLI
subprocess signals are forwarded to the Docker process group. A killed API
process may leave a durable `starting`/recovery posture; it never claims
success, and exact reset is required before another start.

## Element Desktop interoperability checklist

Checklist status: `not_run`; login is blocked until a separately reviewed
transient test-account credential handoff exists. No credential is exposed by
the fixture helper.

1. Confirm the exact pinned image and non-root Compose configuration.
2. Start through the exact lease-governed lane and verify the returned
   lifecycle refs.
3. Configure Element Desktop only for the loopback homeserver URL and confirm
   that federation remains disabled.
4. Use only transient synthetic credentials; never record them in docs,
   receipts, screenshots, logs, or shell history.
5. Verify room, Space, reply, and reaction interoperability without claiming
   E2EE.
6. Log out, stop, run exact reset, and prove zero owned containers, networks,
   volumes, and disposable state.

Until all six items run successfully, Element interoperability remains
`configuration_required`, not product evidence or a claim that UAA Messenger
is connected.

command-bound lease issue, start, governed inspect, internal plus host-loopback

login, connector runtime, encrypted messaging, or product readiness.
